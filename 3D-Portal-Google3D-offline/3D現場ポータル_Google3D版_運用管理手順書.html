運用管理手順書

ポータルを24時間動くLinuxサーバに置き、安全に、お金をかけすぎずに使い続けるための手順をまとめます。

文書番号GP3D-OPS-001
版1.0
作成日2026年10月8日
対象3D-Portal-Google3D.html ／ Linux（nginx）／ Google Cloud（Map Tiles API）
読む人システム管理者・運用担当者

1はじめに

1.1この手順書の目的

この手順書は、「3D現場ポータル 全国版（Google 3D版）」を24時間動いている社内のLinuxサーバに置いて、次の3つを守りながら使い続けるための作業をまとめたものです。

① 止めない

見たいときにいつでも開ける。止まってもすぐ気づいて直せる。

② お金をかけすぎない

Google の料金が、思わぬ額にならないように上限と見張りをつける。

③ キーと規約を守る

APIキーが悪用されないようにし、Google の利用条件を守る。

④ 記録を残す

いつ・だれが・何を変えたかを残し、ISMS の点検に答えられるようにする。

1.2前提

項目前提
サーバ社内の24時間稼働のLinux。Ubuntu 22.04／24.04 LTS または RHEL 9 系（Rocky Linux・AlmaLinux など）
Webサーバnginx（エンジンエックス）。ファイルを配るだけで、プログラムやデータベースは使わない
置くもの3D-Portal-Google3D.html（約670KB）。必要に応じてオフライン版と3つの手順書も
Google Cloud地図専用のプロジェクト1つ。請求先アカウントをリンク済み。Map Tiles API を有効化済み
見る人社内のPC（Chrome／Edge）。社外に見せる場合は 5.5

1.3役割分担

役割やること担当（記入）
サービス責任者使う目的・公開範囲・予算を決める。費用と規約の責任を持つ　
Google Cloud 管理者プロジェクト・請求先・APIキー・上限・予算アラートの設定と見張り　
サーバ管理者Linux・nginx・証明書・ファイルの配置と更新・ログの確認　
ネットワーク管理者FortiGate など、社内から外への通信の許可　
問い合わせ窓口利用者からの質問を受け、上の担当へつなぐ　
請求先が個人のアカウントのとき

いまは請求先が個人のアカウントになっています。料金と規約の責任は、その個人にかかります。試しに使う間はかまいませんが、本番で使う前に会社の請求先へ移してください（9.4）。会社の経費として扱えるかは、先に経理に確認してください。

2システムの構成

2.1構成図

大事なのは、Google の3Dを取りに行くのはサーバではなく利用者のPCだということです。そのため、社内の各PCから ②③ への通信が許可されている必要があります。

2.2通信の一覧

番号どこからどこへポート中身
①利用者のPCLinuxサーバ443（HTTPS）、または 80ポータルのHTML
②利用者のPCcdn.jsdelivr.net443CesiumJS 1.145.0（本体・作業用スクリプト・画像）
③利用者のPCtile.googleapis.com443Google の実写3D（キーつき）
—利用者のPCassets.ion.cesium.com443帰属表示の Google ロゴ画像（届かなくても動くが、ロゴが出ない）
—管理者のPCconsole.cloud.google.com443Google Cloud の設定画面
FortiGate の設定で気をつけること
  • Webフィルタで ②③ のドメインがブロックされていないこと。
  • SSLの中身を検査している場合、社内のPCが FortiGate の証明書を信頼していること（信頼していないと、ブラウザがつながらない）。
  • Google の3Dはデータ量が多い（あちこち見て回ると1回で数百MBになることもある）ため、帯域の制限やアプリ制御で遅くならないこと。

3Google Cloud の準備

すべて https://console.cloud.google.com/ で行います。画面の上部のプロジェクト選択が、地図専用のプロジェクトになっているかを、毎回確かめてから作業してください。

3.1地図専用のプロジェクトを作る

  1. 上部のプロジェクト選択 → 新しいプロジェクト を押します。
  2. 名前を付けます（例：site-portal-3d）。Gemini など、ほかの用途のプロジェクトと分けると、料金と権限が混ざりません。
  3. 作成 を押し、できたプロジェクトを選びます。

3.2請求先アカウントをリンクする（必須）

ここを忘れると、つながりません

請求先アカウントがリンクされていないと、キーが正しくても Google から「404 Requested entity was not found」が返り、3Dが出ません（実際にこの原因で接続できなかった事例があります）。無料の範囲だけで使う場合もリンクが必要です。

  1. 左上のメニュー → お支払い を開きます。
  2. 「このプロジェクトには請求先アカウントがありません」と出たら、請求先アカウントをリンク を押し、使う請求先アカウントを選びます。
  3. お支払い画面に、請求先アカウントの名前が出ていれば完了です。

3.3Map Tiles API を有効にする

  1. https://console.cloud.google.com/apis/library/tile.googleapis.com を開きます。
  2. 青い 有効にする を押します。管理 と出ていれば、すでに有効です。

3.4APIキーを作って制限をかける

  1. APIとサービス → 認証情報 → 認証情報を作成 → APIキー を押します。
  2. できたキーの名前を分かりやすくします（例：site-portal-3d-社内）。
  3. アプリケーションの制限で ウェブサイト を選び、使うサイトを1行ずつ追加します（下の表）。
  4. API の制限で キーを制限 を選び、Map Tiles API だけにチェックを入れます。
  5. 保存 を押します。反映まで最大5分かかります。
置き場所ウェブサイトの制限に登録する値
社内Linux（HTTPS）https://portal.example.local/*（実際のホスト名に置きかえ）
社内Linux（HTTP、IPで開く）http://192.168.10.20/*（実際のIPに置きかえ）
手元の試験（python の簡易サーバ）http://localhost:8000/*（試験が終わったら消す）
GitHub Pageshttps://アカウント名.github.io/*
フォルダ名まで書かない

ブラウザは Google へ「サイト名」（例：https://portal.example.local/）だけを送ります。そのため https://portal.example.local/portal/* のようにフォルダ名まで入れて登録すると一致せず、拒否されます。必ず サイト名＋/* で登録してください。

キーを作るのは「社内用」「社外公開用」など、使い道ごとに分けると、止めるときに影響を小さくできます。

3.5予算アラートを設定する

  1. お支払い → 予算とアラート → 予算を作成 を押します。
  2. 対象を地図専用のプロジェクトにします。
  3. 金額を決めます（例：月 1,000円）。
  4. 通知のしきい値を 50%・90%・100% にし、メールの送り先に担当者を入れます。
予算アラートは「知らせる」だけ

予算を超えても、自動では止まりません。止める役目は、次の「1日の上限」が受け持ちます。

3.61日の上限（割り当て）を下げる

  1. APIとサービス → 有効なAPIとサービス → Map Tiles API → 割り当てとシステムの上限 を開きます。
  2. 3D タイル（ルートタイルセット）の1日あたりの回数の項目をさがします（初期値は1日10,000回。画面によって表示名が少しちがいます）。
  3. 鉛筆の印で編集し、使う人数に合わせて下げます（例：1日100回）。

上限に達すると、その日は「利用上限（クォータ）に達しています」と表示され、利用者は簡易地形モードで使い続けられます。次の日に回復します。

3.7キーが使えるか確かめる

ポータルを置いたサーバのURLで開き、右上が緑の Google 実写3D（オンライン） になれば成功です。失敗したときは、APIキー画面の赤い枠に原因が出ます（10.2）。

ブラウザのアドレス欄に https://tile.googleapis.com/v1/3dtiles/root.json?key=キー を入れて確かめる方法もあります。ただし、ウェブサイトの制限をかけたキーは、アドレス欄からでは「Requests from referer … are blocked」と出ます。これは正常です（制限が効いている証拠）。

4Linux サーバの構築

4.1nginx を入れる

Ubuntu

sudo apt update sudo apt install -y nginx sudo systemctl enable --now nginx

RHEL 9 系

sudo dnf install -y nginx sudo systemctl enable --now nginx

止まったときに自動で起き上がるように、再起動の設定を足します（両方共通）。

sudo mkdir -p /etc/systemd/system/nginx.service.d printf '[Service]\nRestart=on-failure\nRestartSec=5s\n' | sudo tee /etc/systemd/system/nginx.service.d/restart.conf sudo systemctl daemon-reload sudo systemctl restart nginx

4.2置き場所を作る

更新しても、すぐ元にもどせるように、版ごとのフォルダを作り、公開フォルダはその版への「近道（シンボリックリンク）」にします。

sudo mkdir -p /var/www/releases # 公開フォルダ：/var/www/site-portal → /var/www/releases/版の名前（5.3 で作る）
場所中身
/var/www/releases/20261008-1/ある版のファイル一式（index.html など）
/var/www/site-portalいま公開している版への近道
/var/log/nginx/site-portal.access.logだれ（どのPC）がいつ開いたかの記録
/etc/nginx/nginx の設定

4.3nginx の設定

設定ファイルを作ります。置き場所は Ubuntu が /etc/nginx/sites-available/site-portal、RHEL 系が /etc/nginx/conf.d/site-portal.conf です。中身は 付録A の全文を使い、portal.example.local・証明書の場所・社内のIP帯を自分の環境に合わせます。

Ubuntu

sudo nano /etc/nginx/sites-available/site-portal sudo ln -s /etc/nginx/sites-available/site-portal \ /etc/nginx/sites-enabled/ sudo rm -f /etc/nginx/sites-enabled/default sudo nginx -t && sudo systemctl reload nginx

RHEL 9 系

sudo vi /etc/nginx/conf.d/site-portal.conf sudo nginx -t && sudo systemctl reload nginx

nginx -t で「syntax is ok」「test is successful」と出てから reload します。エラーのまま reload しないでください。

CSP（Content-Security-Policy）は設定しない

セキュリティ強化のための CSP ヘッダを付けると、CesiumJS の作業用スクリプトが止まり、地球や地形が出なくなることを確認しています。付録Aの設定には入れていません。Referrer-Policy は strict-origin-when-cross-origin（ブラウザの標準）のままにしてください。no-referrer にすると、Google のウェブサイトの制限で拒否されます。

4.4HTTPS にする

社内だけで使う場合と、社外にも公開する場合で、証明書の作り方がちがいます。

使い方証明書手順の要点
社内だけ社内の認証局（AD CS など）が発行した証明書サーバで鍵と申請書（CSR）を作り、社内の認証局に発行してもらう。社内PCはグループポリシーで認証局を信頼済みであること
社外にも公開Let's Encrypt（無料）公開DNS名と、インターネットから80番に届くことが必要。certbot で自動更新

社内の認証局に出す申請書を作る

sudo mkdir -p /etc/ssl/site-portal && cd /etc/ssl/site-portal sudo openssl req -new -newkey rsa:2048 -nodes \ -keyout privkey.pem -out request.csr \ -subj "/CN=portal.example.local" \ -addext "subjectAltName=DNS:portal.example.local" sudo chmod 600 privkey.pem # request.csr を認証局に出し、発行された証明書（中間証明書を含む）を fullchain.pem として保存

Let's Encrypt（社外公開のとき）

Ubuntu

sudo apt install -y certbot python3-certbot-nginx sudo certbot --nginx -d portal.example.com

RHEL 9 系

sudo dnf install -y epel-release sudo dnf install -y certbot python3-certbot-nginx sudo certbot --nginx -d portal.example.com

4.5ファイアウォール

Ubuntu（ufw を使っている場合）

sudo ufw allow 'Nginx Full' sudo ufw status

RHEL 9 系（firewalld）

sudo firewall-cmd --permanent --add-service=http --add-service=https sudo firewall-cmd --reload

4.6SELinux（RHEL 系だけ）

RHEL 系では、/var/www の下に置いたファイルに、Webで配ってよい印を付けます。ファイルを置いたあとに毎回実行します。

sudo restorecon -Rv /var/www/releases /var/www/site-portal

nginx の記録に「Permission denied」と出たときは、まずこれを実行してください。

4.7時刻とOSの自動更新

  • 時刻：証明書や記録の時刻が狂わないように、時刻合わせ（chrony／systemd-timesyncd）が動いていることを timedatectl で確かめます（「System clock synchronized: yes」）。
  • OSの更新：Ubuntu は unattended-upgrades、RHEL 系は dnf-automatic で、セキュリティ更新を自動で入れます。再起動が必要な更新は、決めた時間（例：毎月第2水曜の夜）に行います。

5配置と公開

5.1ファイル名のきまり

公開する名前中身URLの例
index.htmlGoogle 3D版（3D-Portal-Google3D.html の名前を変えたもの）https://portal.example.local/
offline.htmlオフライン版（必要なら）https://portal.example.local/offline.html
docs/spec.html など詳細仕様書・利用手順書・この手順書（必要なら）https://portal.example.local/docs/guide.html

日本語や空白を含む名前は、URLが長く読みにくくなるので使いません。

5.2キーをファイルに書きこむか決める

やり方向いている場合注意
A. 書きこまない（初期のまま）見る人が少なく、キーを個別に渡せる。キーのない人は簡易地形でよいキーを受けとった人が、それぞれのブラウザで入力する
B. 書きこむ（EMBED_GOOGLE_KEY）社内の多くの人や社外の人に、キー入力なしで見せたいページを開ける人は全員キーを見られる。ウェブサイトの制限・API制限・1日の上限・予算アラートの4つを必ず設定してから行う

B を選んだときは、キーを書きこんだファイルを、メールやチャットで配ったり、共有フォルダに置いたりしないでください。サーバの公開フォルダにだけ置きます。

5.3配置の手順

  1. Windows からサーバへ送る（PowerShell の例。WinSCP でドラッグしてもかまいません）。
    scp "D:\みらいサンプルプロダクトアイデア\オフライン3D現場ポータル 全国版\3D-Portal-Google3D.html" ユーザー名@サーバ名:/tmp/
  2. 版のフォルダを作って入れる（サーバで実行）。
    REL=/var/www/releases/$(date +%Y%m%d-%H%M) sudo mkdir -p "$REL" sudo cp /tmp/3D-Portal-Google3D.html "$REL/index.html"
  3. （B を選んだときだけ）キーを書きこむ。キーが画面や記録に残らないように、伏せ字で入力します。
    read -rsp 'APIキー: ' KEY; echo sudo sed -i "s/const EMBED_GOOGLE_KEY = '';/const EMBED_GOOGLE_KEY = '${KEY}';/" "$REL/index.html" unset KEY sudo grep -c "EMBED_GOOGLE_KEY = 'AIza" "$REL/index.html" # 1 と出れば成功
  4. 持ち主と権限をそろえる。
    sudo chown -R root:root "$REL" && sudo chmod -R a+rX "$REL" sudo restorecon -Rv /var/www/releases # RHEL 系だけ
  5. 公開を切りかえる（一瞬で切りかわり、見ている人に影響しません）。
    sudo ln -sfn "$REL" /var/www/site-portal ls -l /var/www/site-portal
  6. 確かめる：5.4 のチェックリストを行い、記録（付録C）に版の名前を書きます。
  7. 後かたづけ：sudo rm /tmp/3D-Portal-Google3D.html

5.4公開前チェックリスト

  • 社内のPC（Chrome と Edge）で URL を開き、右上が緑の「Google 実写3D（オンライン）」になる
  • 日本全体に15か所のピンが出る
  • 現場を2〜3か所開き、施工範囲の地面が周りとほぼ段差なくつながり、本物の建物と架空の建物が重なっていない
  • 左下に Google のロゴとデータ提供元の表示が出ていて、ほかの表示で隠れていない
  • 現場表示で「工事・建物計画はすべて架空のサンプルです」が出ている
  • タイムラインの再生・管理パネルのタブが動く
  • キーの制限が「ウェブサイト（サイト名/*）」「Map Tiles API のみ」になっている
  • 予算アラートと1日の上限が設定されている
  • 証明書のエラーが出ない（鍵のマークが出る）
  • 社外のネットワークから開けない（社内限定の場合）

5.5社外の人に見せる場合

方法よいところ気をつけること
GitHub Pages に置くサーバの公開設定がいらない。HTTPS が自動だれでも開ける。キーを書きこむ場合は4つの守りを必ず設定。リポジトリを公開にするとファイル（キー）も見られる
社内Linuxを外に公開社内の管理下に置けるFortiGate で公開設定（VIP）、Let's Encrypt、パスワード（下の Basic 認証）、アクセス記録の確認が必要

パスワードをかける（Basic 認証）

# Ubuntu: sudo apt install -y apache2-utils ／ RHEL 系: sudo dnf install -y httpd-tools sudo htpasswd -c /etc/nginx/.htpasswd guest # パスワードを2回入力 # 付録Aの「Basic 認証」の2行の先頭の # を外して reload

パスワードで守っても、ページを開ける人にはキーが見えます。キーの4つの守りは外さないでください。

6日々の運用

6.1点検の予定

いつ点検することやり方
毎日（自動でもよい）ページが開けるかcurl -sk -o /dev/null -w '%{http_code}\n' https://portal.example.local/ が 200
毎週nginx が動いているか・エラーが増えていないかsystemctl status nginx、sudo tail -n 50 /var/log/nginx/site-portal.error.log
毎週開かれた回数（≒ Google の課金回数）6.2 のコマンド
毎月Google の料金と使用量お支払い → レポート、Map Tiles API の指標（6.3）

毎月証明書の期限付録B のコマンド。30日を切ったら更新

6.2アクセス記録の見方

ポータルを1回開くと、ふつう Google の課金が1回数えられます。nginx の記録から、開かれた回数の目安が分かります。

# 今日、ポータルが開かれた回数（200=新しく取得、304=キャッシュの確認） sudo awk -v d="$(LC_ALL=C date +%d/%b/%Y)" '$4 ~ d && $7 ~ /^\/(index\.html)?(\?.*)?$/ && ($9==200||$9==304)' \ /var/log/nginx/site-portal.access.log | wc -l # 日ごとの回数（記録に残っている期間） sudo awk '$7 ~ /^\/(index\.html)?(\?.*)?$/ && ($9==200||$9==304){split($4,a,":"); print substr(a[1],2)}' \ /var/log/nginx/site-portal.access.log | sort | uniq -c # よく開いているPC（IP）上位10 sudo awk '$7 ~ /^\/(index\.html)?$/{print $1}' /var/log/nginx/site-portal.access.log | sort | uniq -c | sort -rn | head

同じ人が何度も読み直すと、そのたびに数えられます。急に増えたときは、だれが開いているかを確かめます。

6.3Google 側の使用量と料金の見方

  1. APIとサービス → Map Tiles API → 指標：日ごとのリクエスト数・エラーの数。エラーが多いときは、キーの制限や上限に当たっています。
  2. お支払い → レポート：プロジェクト・サービスごとの料金。
  3. nginx の記録の回数（6.2）と、Google の数がおおむね合っているかを見ます。Google の数だけが大きく多いときは、キーがほかの場所で使われている（漏れた）おそれがあります（8.3）。

8APIキーの管理

8.1キーの約束

  • キーは「ウェブサイトの制限（サイト名/*）」と「Map Tiles API のみ」の2つの制限を必ずかける
  • キーは使い道ごとに分ける（社内用・社外公開用・試験用）
  • キーをメール・チャット・資料・チケットに書かない。渡すときは、パスワード管理ツールや、期限つきの安全な共有方法を使う
  • キーをGitのリポジトリに入れない（GitHub Pages に置くときは、キーを書きこむかを特に慎重に決める）
  • 試験用のキーや localhost の許可は、試験が終わったら消す
  • キーの一覧（名前・使い道・作った日・入れかえ予定日）を管理表に残す

8.2定期的な入れかえ（3か月ごとをすすめる）

  1. 3.4 の手順で、同じ制限の新しいキーを作ります。
  2. キーを書きこんでいる場合は、5.3 の手順で新しいキーの版を作って切りかえます。書きこんでいない場合は、利用者に新しいキーを配り、🔑 APIキー から入れ直してもらいます。
  3. 1〜2日、新しいキーで使えていることを確かめます（6.3 の指標）。
  4. 古いキーを 認証情報 の画面で削除します。
  5. 管理表を更新します。

8.3キーが漏れたかもしれないとき

すぐにやること（順番どおり）
  1. Google Cloud の 認証情報 で、そのキーを削除します。削除したキーは、すぐに使えなくなります。
  2. 新しいキーを作り（3.4）、ポータルを切りかえます（5.3）。
  3. お支払い → レポート と Map Tiles API の指標で、いつから・どれだけ使われたかを確かめます。
  4. サービス責任者に報告し、情報セキュリティの事故として記録します。思わぬ料金が出ていれば、Google Cloud のサポートに相談します。
  5. 漏れた原因（ファイルの配布、画面の写真、Git など）を調べ、同じことが起きないようにします。

9.3上限の決め方

  1. 月の予算を決めます（例：1,000円）。
  2. 予算で使える回数を計算します。例：1,000円 ≒ 6.5ドル（1ドル＝155円のとき）→ 無料1,000回＋約1,080回 ≒ 月2,000回。
  3. 1日の上限を「月の回数 ÷ 30」くらいにします（例：1日70回）。会議などで多く使う日は、その日だけ上げます。
  4. 予算アラートを、その予算の 50%・90%・100% で設定します（3.5）。

9.4個人の請求先から会社の請求先へ移す

  1. 会社の請求先アカウント（会社のクレジットカードまたは請求書払い）を、会社として用意します。
  2. 会社の管理用アカウントを、プロジェクトの IAMと管理 で「オーナー」に追加します。
  3. お支払い → 請求先アカウントを変更 で、会社の請求先アカウントに切りかえます（キーやAPIの設定はそのまま使えます）。
  4. 予算アラートを会社の請求先側で作り直し、通知先を会社の担当者にします。
  5. 個人のアカウントの権限を、必要最小限（または削除）にします。
  6. 切りかえた日を記録し、以後の料金が会社に請求されていることを、翌月の請求で確かめます。

10障害への対応

10.1切り分けの順番

  1. どこまで開けるかを利用者に聞きます：ページ自体が開かない／開くが3Dが出ない／簡易地形は出るが Google 3D が出ない。
  2. 右上の札と、赤い枠の原因を教えてもらいます（キーは聞かない）。
  3. 1人だけか、全員かを確かめます。全員ならサーバかネットワーク、1人ならそのPCかブラウザが原因のことが多いです。
  4. 下の表で原因を絞り、直したら利用者に Ctrl＋F5 で開き直してもらいます。

server { listen 80; server_name portal.example.local; return 301 https://$host$request_uri; # HTTP は HTTPS へ転送 } server { listen 443 ssl; server_name portal.example.local; ssl_certificate /etc/ssl/site-portal/fullchain.pem; ssl_certificate_key /etc/ssl/site-portal/privkey.pem; ssl_protocols TLSv1.2 TLSv1.3; root /var/www/site-portal; index index.html; charset utf-8; server_tokens off; # 社内からだけ（社内のIP帯に合わせる） allow 10.0.0.0/8; allow 172.16.0.0/12; allow 192.168.0.0/16; deny all; # 社外に公開してパスワードをかけるとき（5.5） # auth_basic "3D Portal"; # auth_basic_user_file /etc/nginx/.htpasswd; # HTML は毎回、新しいかを確かめる add_header Cache-Control "no-cache" always; add_header X-Content-Type-Options "nosniff" always; add_header X-Frame-Options "SAMEORIGIN" always; add_header Referrer-Policy "strict-origin-when-cross-origin" always; # Content-Security-Policy は付けない（CesiumJS が止まるため） gzip on; gzip_types text/css application/javascript application/json image/svg+xml; # text/html は gzip on だけで圧縮される access_log /var/log/nginx/site-portal.access.log; error_log /var/log/nginx/site-portal.error.log; location / { try_files $uri $uri/ =404; } }
