1はじめに

1.1この文書の目的

この文書は「みらい建設工業 3D現場ポータル（港湾・海洋土木版／Google 3D版）」が、どんな画面で、どんなデータを使い、どんな計算をして、どう3Dで見せるか、そしてGoogle の実写3Dとどうつながるかを細かく決めた設計書です。作った人以外が読んでも、同じものを作り直したり、機能を足したりできることを目指しています。

このシステムは、原本「3D現場ポータル 全国版（Google 3D版）」を、みらい建設工業の業務（港湾・海岸・陸上土木の工事、7支店と作業所の体制、国・自治体・港湾管理者・民間という発注区分）に合わせて作り直したものです。計算の仕組みは原本と同じで、工事の種類・現場の置き方・台帳の項目・3Dの構造物を入れかえています。原本のファイルは変えていません。

むずかしい言葉は、できるだけふつうの言葉に言いかえています。専門用語が必要なところは、すぐあとに意味を書きます。巻末の「用語集」もあわせて見てください。

1.4読み方の約束

  • ボタン名 のように枠で囲んだ言葉は、画面に表示される文字です。
  • 計算式は このような書き方 または灰色の枠で示します。× はかけ算、÷ はわり算です。
  • 「地山」「ほぐし」「締固め」など土の量の言葉は、6.4 と用語集で説明します。
  • 「Google 3D」「実写3D」は、Google Map Tiles API の Photorealistic 3D Tiles（写真から作った立体の地図）のことです。
  • 次の4つの言葉を使い分けます。架空＝実在しない工事・発注者・工程。仮採番＝正式な規則で決めたものではない番号。仮定＝確認していない前提（港湾ごとの担当支店など）。サンプル値＝実務の値ではない係数（地域係数・機械の能力・燃料の原単位など）。
  • 「原本」は「3D現場ポータル 全国版（Google 3D版）」（3D-Portal-Google3D.html）とその詳細仕様書のことです。

2システムの概要

2.1このシステムでできること

  • 地球儀のような日本の上に、7支店が担当する港湾・海岸・臨港地区の工事現場17か所（陸の15か所と、浚渫・海面埋立の2か所。すべて架空）をピンで表示します。ピンの色で、工事が遅れそうかどうかが分かります。
  • 支店・都道府県・工種区分（港湾／海岸／陸上土木／港湾建築）・発注区分（官公庁／民間）で現場を絞り込み、支店ごとの現場数・平均進捗・遅延予測の数を見られます。
  • ピンを選ぶと、その現場へ飛んでいき、Google の実写3Dの港の街並みの中に、工事中の地面と、ヤードの舗装・護岸・防潮堤の堤体・臨港道路・倉庫・重機を3Dで表示します。
  • 工事前の地面と工事後の地面（計画地盤高）の差から、掘る土の量（切土）と盛る土の量（盛土）を計算し、余る土（残土）と足りない土（搬入土）を出します。ふ頭用地の嵩上げのように盛土だけの工事では、搬入土の量と、それを運ぶダンプの台数が分かります。
  • 重機の台数・天気・冬の雪などの条件から、工事がいつ終わりそうかを1日ずつ予測します。
  • 画面下のタイムラインを動かすと、過去（実績）や未来（予測）の現場のようすを3Dで見られます。
  • 重機の台数や計画地盤高を変えると、予測がすぐに計算し直されます（What-if＝「もし〜だったら」の比較）。

原本を変えずに作る原本のHTMLを読み、決まった場所だけを置きかえてアプリを作る（4.9）。置きかえる場所が見つからない・複数あるときは作るのをやめる原本が直ったときに作り直しやすくし、思わぬ所を書きかえないため
キーを書きこまないサーバ版では、Google のAPIキーをサーバの server/.env（GOOGLE_MAP_TILES_KEY）に置き、ログインした人にだけ渡す。ファイル（online/data/config.json を含む）には書かない。静的な配信・埋め込み版では、画面で入れてそのブラウザにだけ保存する。キーは DX推進部が発行・管理する会社のキーを使うファイルを配ってもキーが広まらないようにし、費用の請求先を会社にそろえるため
つながらなくても使えるGoogle につながらないときは、自動で簡易地形モードにするキーがない人・社内ネットワークの制限がある人も使えるようにするため

規約を守る作り帰属表示を画面に出す、保存しない、Google 以外の住所検索の結果を Google の3Dに重ねないGoogle Map Tiles API の利用条件に合わせるため（8.7）

4.2データの小さくし方

  • 線（境界・道路）：緯度・経度を1000倍して整数にし、最初の点だけそのまま、2点目からは「前の点との差」で記録します。差は小さな数になるので、文字数が減ります。

  • この結果、埋め込みデータ（const GEO = … の1行）は517,727バイト（約0.5MB）、HTML全体で678,660バイトに収まっています（版1.0 の時点。2026-10-20 の埋め込み版は機能の追加で 728,617 バイト）（3D描画ライブラリ CesiumJS はファイルに含めず、開くときにインターネットから読み込みます）。

4.8現場データの作り方

施工範囲は、実在の港湾地区の中に、プログラムで自動で置いた仮の範囲です。実在の工事・計画・土地の使い方とは関係ありません。作り方は次のとおりです（tools/gen_sites.py）。

  1. 探す範囲を決める：港ごとに、探索の中心（経度・緯度）、施工範囲の大きさ、条件を tools/specs.json に書きます（下の表）。探す半径は2,500m（水島港だけ4,000m）です。
  2. 標高を集める：半径＋1,200mの範囲の国土地理院 標高タイルを、DEM5A（ズーム15）→ DEM5B（ズーム15）→ DEM10B（ズーム14）の順に重ね、データのある点を使います。5m間隔の格子で標高を取ります。
  3. 候補を調べる：格子を4マスずつずらしながら、施工範囲の四角を置いてみます。次の条件をすべて満たすものを候補にします。
    • 四角の中に、標高データのない点（海・川など）が1つもない（陸域だけ）
    • 四角の中の標高の中央値と、起伏（最高−最低）が、決めた範囲に入る
    • 「水域に接する」と決めた工種では、四角の外側50mの帯のうち、いちばん水域の多い辺で、標高データのない点が35%以上ある。その辺を水域側（sea）にする
  4. いちばん良い候補を選ぶ：点数＝探索の中心からの距離(km)＋起伏×0.05（起伏の上限が20m以上の工種は −起伏×0.02）−水域の割合（水域に接する工種だけ）、がいちばん小さい候補を選びます。防潮堤は、東西に長い形（240×70m）と南北に長い形（70×240m）の両方を試し、長い辺が水域に接するものだけを候補にします。
  5. 地形を切り出す：施工範囲（4m間隔）と周り1km四方（12.5m間隔）の標高を取り、周りの標高データのない点を T.P.−1.0m で埋めます（4.1）。
  6. 所在地を求める：施工範囲の中心で国土地理院 逆ジオコーダに問い合わせ、地方公共団体コード表（muni.js）で都道府県・市区町村の名前にします。埋立地などで答えが返らないときは、中心から60・120・250・500・1,000m離れた8方向の点で順に試します。町字に「地先」をつけて所在地にします。

5座標と地図の仕様

座標の扱いは原本と同じです。ちがうのは、県ごとのジオイド高の目安の表（5.3）と、水域に接する現場での地形のつなぎ目（5.4）です。

5.1地球の座標

3Dの表示は、CesiumJS の地球中心の座標（地球の中心を原点にした、単位mの座標）で行います。日本全体から現場の数cmまでを1つの座標で扱えるように、CesiumJS が中で精度の工夫をしています。そのため、オフライン版のように「全国はkm、現場はm」と座標を切りかえる必要はありません。

ただし、計算（ワールドモデル）のほうは、オフライン版と同じ現場ごとの座標（5.2）で行います。3Dに出す直前に、地球中心の座標へ変換します。

県境・高速道路の判定や都道府県のクリック判定には、緯度・経度をそのまま使います。支店を選んだときの移動先（3.3）も、その支店の現場の緯度・経度の範囲から決めます。

5.2現場の座標（m）と変換

現場の座標は、施工範囲の中心を原点にして、x が東、y が上、z が南、単位は m です（原本と同じ）。水域側（sea）の N・S・E・W も、この向きで決めます（N＝z がマイナスの辺、S＝z がプラスの辺、E＝x がプラスの辺、W＝x がマイナスの辺）。3Dに出すときは、次の2段階で変換します。

  1. 向きの入れかえ：東＝x、北＝−z、上＝y として「東・北・上（ENU）」の向きにします。
  2. 地球への置きかた：現場の中心（経度・緯度）の、高さ「yRef＋ジオイド高」の地点に ENU を置き、地球中心の座標にします（CesiumJS の eastNorthUpToFixedFrame）。
地球中心の位置 ＝ ENU の置き場所 × 向きの入れかえ × 現場の座標（x, y, z）

構造物や重機の箱は、もとの「1辺1mの箱を、回して・のばして・動かす」という指定を、この変換の間にはさんで使います。のばす量が0に近いときは、計算がこわれないように0.001mにそろえます。

6.5土積曲線と平均運搬距離

西から東へ、列ごとに「流用する切土 × C − 盛土」を足していった線が土積曲線（マスカーブ）です。線が上がる所は土が余り、下がる所は土が足りません。終点の値が全体の余り（＋）または不足（−）です。

場内の平均運搬距離は、余り・不足をゲートの列で受け払いしたことにしてから、各列の境目を通る土の量 × 列の幅 を合計し、運ぶ土の量の合計で割って求めます（土積曲線の面積 ÷ 運搬土量）。本版ではゲートを陸側に置くので（7.4）、水域が東の現場ではゲートが西の辺に、水域が西の現場では東の辺にあります。受け払いの列はゲートの x の位置で決まります。

6.7稼働日（雨・冬）

1日あたりの「働ける量」を稼働係数として、日ごとに計算します。これを積み上げた「累計稼働日」を使って、土工の進み方と終わる日を決めます。

その日の稼働係数 = 稼働日[日/週] ÷ 7 × (1 − 雨天・休止率) × (冬期なら 冬期の土工稼働率、そうでなければ 1)

たとえば北海道（雨天10%、12月〜3月は稼働30%）で週6日なら、冬以外は 6÷7×0.9＝0.77、冬は 0.77×0.3＝0.23 です。冬の間は土工がほとんど進まない、という動きになります。石狩湾新港（HK-2026-0002）は、盛土・嵩上げ（土工）の計画が2026/08/19〜2027/03/27 で冬期にかかるため、竣工が計画より105日遅れる予測になります（付録B）。初期計画で土工が冬期にかかるのは石狩湾新港だけです。冬期のある北海道・宮城県（1月〜2月は稼働80%）のほかの3現場（苫小牧港・仙台塩釜港・石巻港）は、土工が基準日より前の冬期以外の時期に終わっています。What-if で土工を遅らせると、冬期の影響が出ることがあります。

6.8地域係数

都道府県ごとに、雨天・休止率、冬期の期間と土工の稼働率、残土処分場までの標準距離を持ちます（全件は 付録A。原本と同じ）。施工計画の初期値に使い、土工計画タブで変更できます。値はサンプルで、実務では気象庁の平年値や社内の実績に置きかえる前提です。海上の波浪による休止は含みません（12章）。

6.9実績による較正（実効率 η）

重機のカタログ上の能力どおりには、実際の工事は進みません。そこで、基準日までの実績から「実際は能力の何割で進んでいるか」を求め、これを実効率 η として予測に使います。

基準日までの実績土工量 = 土工の実績進捗 × Q 基準日までの稼働日 = 累計稼働日(基準日) − 累計稼働日(土工の開始日) 実際の日当り量 = 実績土工量 ÷ 稼働日 η = 実際の日当り量 ÷ 初期の重機編成での最小能力 （0.35〜1.15 の範囲に収める）

土工が終わっている現場は η＝0.80（参考値）、まだ始まっていない現場も η＝0.80（観測がないための既定値）とします。η は初期の重機編成で一度だけ求め、重機の台数を変えても η は変えません。こうすることで「今のペースのまま台数を増やしたらどうなるか」が分かります。

本版の初期計画では、土工が進行中で実績から η を求めた現場が2つ（石狩湾新港 0.48、水島港 0.79）、土工が始まっていない現場が1つ（北九州港 KS-2026-0001。土工の計画開始 2026/10/09 が基準日より後）、残りの12現場は土工が終わっています。実績は架空なので、η も架空の実績から出した値です。

6.11任意の日の状態の計算

7.2重ね順と切り抜き

Google の3Dは、そのままでは施工範囲の中にも本物の岸壁・建物・木があり、自社の地形や構造物とぶつかります。そこで、施工範囲の四すみ（外側に0.6m広げたもの）で囲んだ範囲だけ、Google の3Dを切り抜いて消します（CesiumJS の ClippingPolygon）。切り抜きは、現場を表示している間だけ、その1現場分だけ行います。全国表示に戻ると切り抜きを外します（原本と同じ）。

切り抜きの見え方

施工範囲の境目にかかる本物の建物や岸壁は、途中で切られた形（中が空の殻のような形）に見えることがあります。Google の3Dは表面だけのデータなので、切った面は中が見えます。不具合ではありません。施工範囲は自動で置いた仮の範囲なので、実在の倉庫や道路にかかることがあります（12章）。

8.5高さ合わせ（ジオイド高の自動補正）

現場へのカメラの移動が終わったら、現場の周りの Google の地面の高さを調べて、自社の地形の高さを合わせます（原本と同じ）。

  1. 施工範囲の外側に、3重の輪（施工範囲の1.2倍・1.5倍・1.9倍＋12m）を考え、それぞれ16か所、合わせて最大48か所の点を選びます。周辺地形データの外（中心から470m以上）は使いません。
  2. それぞれの点で、Google の3Dの一番上の高さ（楕円体高）を調べます（CesiumJS の sampleHeightMostDetailed。自社の地形・構造物は除いて調べる）。
  3. 同じ点の標高（国土地理院の周辺地形）との差を計算します。差＝その点でのジオイド高の候補です。
  4. 差を小さい順に並べ、下から20%の値を採用します。建物や木の上に当たった点は差が大きくなるので、低いほうを使うと地面の値に近くなります。
  5. 使える点が8か所以上あり、値が15〜60mの範囲なら採用します。いまの値と0.25mより大きくちがうときは、地形・構造物・切り抜きを作り直し、カメラの位置も保ったまま合わせ直します。

うまく調べられなかったときは、県ごとの目安の値（5.3）のまま表示を続けます。合わせた結果は、その画面を開いている間だけ覚えておきます。

水域に接する現場での注意

周りの輪の点のうち海の上にあるものは、国土地理院の標高が埋め値（T.P.−1.0m）なので、差は本当のジオイド高にはなりません。海の上の点が多い現場では、合わせた高さが目安とずれることがあります。本版ではこの点を確かめていません（未確認）。気になるときは、Google 3D レイヤーを切りかえて、岸壁の高さと自社の地形を見比べてください。

9住所照合の仕様

住所の文字から、市区町村（政令市は区）の代表地点を、インターネットを使わずに探す仕組みです。中身は原本・オフライン版と同じで、簡易地形モードのときだけ使えます。

  1. 入力から空白を除き、全角・半角をそろえます。
  2. 先頭が都道府県名（「東京都」または「東京」）なら、その県の中だけを探します。
  3. 残りの文字が市区町村名で始まる、または市区町村名が残りの文字で始まるものを候補にし、長く一致したものから最大3件を出します。
  4. 市区町村が見つからず都道府県だけ分かったときは、県庁の位置を出します。
Google 3D 表示中に止める理由

Google の実写3Dは、Google 以外の住所検索（ジオコーダー）の結果と組み合わせないことが求められています（8.7）。そのため、Google 3D を表示している間は、候補の表示・Enter での移動・白い印をすべて止め、サマリにその旨を表示します。工事番号・工事名・港名・支店名・所在地の文字での台帳の検索は、いつでも使えます。

現場の所在地とのちがい

この住所照合（ABR の市区町村の代表地点）と、現場の所在地（国土地理院 逆ジオコーダで求めた町字＋「地先」。4.8）は別のものです。現場の所在地は、データを作るときに一度だけ求めて文字として埋め込んであり、画面を開いているときに問い合わせることはありません。

12制約と今後の拡張

いまの制約

  • ファイルをダブルクリックで開くと動きません。CesiumJS の作業用スクリプトが file:// では読めないためです。開いたときは注意のお知らせを出します。
  • オフラインでは Google 3D は使えません。規約で保存が禁止されているためです。
  • 陸の15現場は陸上の工事だけを表します。国土地理院の標高データは陸域だけで海底がないため、護岸の前面（海側）の工事や水中の基礎は扱えません。浚渫・海面埋立は、架空の深浅測量を使う架空の2現場だけです（1.3）。実際の深浅測量はサーバ版の「測量の比較」タブで登録できますが、登録した測量で土量・工程を計算し直すのはその画面だけで、台帳の予測は変わりません（18.6）。
  • 施工範囲は自動で置いた仮の範囲です。標高の条件だけで選んでいるので、実在の岸壁・倉庫・道路・鉄道と重なることがあります。実在の港湾の利用状況・土地の持ち主・港湾計画とは関係ありません。架空の工事として見てください。
  • 水域の表示は目安です。標高データのない所を一律に T.P.−1.0m の平らな面で描くので、本当の水深・潮位・海底の形ではありません。色は「埋めた値と同じ高さか」で決めるので、海面より低い干拓地など、標高データのある低い土地は水色になりません（石巻港・熊本港の周りには T.P.−1.0m より低い標高データの点があり、緑〜茶色で描かれます）。標高データがちょうど T.P.−1.00m の点があれば水色になりますが、まれです。
  • 護岸・堤体・舗装・中央分離帯は、区間ごとの簡単な箱です。断面の形（法勾配・消波ブロック・パラペットなど）や、その材料の量は表しません（6.2）。
  • 港湾ごとの担当支店の割り当ては仮定、工事番号は仮採番、地域係数・機械の能力・燃料の原単位はサンプル値です。
  • Google の3Dは、場所によって細かさや撮影時期がちがいます。埋立地や港では、撮影後に建物や岸壁が変わっていることがあります。
  • 切り抜きの境目で、本物の建物が途中で切れた形に見えることがあります（7.2）。
  • 高さ合わせは目安です。Google の地面と国土地理院の標高は、数十cm〜1m程度ずれることがあります。水域に接する現場での高さ合わせの確からしさは確かめていません（8.5）。
  • アプリ内プレビュー、メール添付のプレビューでは、外への通信が止められるため Google 3D は表示できません。

15.4他のサイトからの送信を防ぐ仕組み（CSRF 対策）と応答のヘッダ

  • 変更系の API（POST・PUT・DELETE）は独自ヘッダ X-Portal-Request: 1 が必須。Origin があれば、このサーバと同じであること。CORS は許可しない。
  • すべての応答に X-Content-Type-Options: nosniff・X-Frame-Options: DENY・Referrer-Policy: strict-origin-when-cross-origin（Google のキーのリファラ制限に合わせ、他サイトへはオリジンだけを送る）。/api/ には Cache-Control: no-store。
  • API の説明ページ（/docs・/redoc・/openapi.json）は出さない。決めた道以外は 404。
  • エラーは {"error": "日本語の理由"} で返す。入力の誤りは 400 または 422、制約違反（参照先が無いなど）は中身を出さずに 400。

18.2気象・海象

現場の市区町村に当たる気象庁の予報区域の天気・風・波と、発表中の警報・注意報（2026-05-28 からの新しい警報体系）を出します。水際の工種（防潮堤・ふ頭用地造成・ふ頭ヤード・浚渫・埋立）は、波の高さで作業判断の目安を出します（注意 1.5m／中止 2.5m。サンプル値。master.json の marine）。台帳に「⚠気象／⚠中止目安」、絞り込みに「気象注意」、全社サマリに件数を出します。起動の後と30分ごとに取り直します。いまの実際の予報なので、工程の計算（基準日 2026-10-06 の架空データ）には入れません。気象庁につながらなくてもポータルは動きます。

18.3潮位

最寄りの潮位表地点（気象庁）の推算潮位、満潮・干潮、干潮時の作業時間帯（平均海面より 20cm 以上低い時間。サンプル値。marine.tideWork）を出します。「1日の潮位を再生」で 3D に潮位面を出して動かします。T.P. への換算は気象庁の MSL 標高を使い、不明な地点は MSL≒T.P. の概算です。

18.4作業可能日

18.5配船（サーバ版）

  • 作業船ごとの割り当てを全現場のガント（30日前〜180日後）で出し、今後180日の稼働率（割り当てのある日の割合）を出します。
  • 海上工事の現場では、「浚渫・埋立（土工）」の予測期間と、ワールドモデルの編成（浚渫・積込＝バックホウ欄の隻数、運搬＝ダンプ欄の隻数）に対する割り当ての不足日を出します。
  • 同じ船を同じ期間に2つの現場へ割り当てると、サーバが止めて重なった割り当てを返します（409）。同時に保存しても重ならないよう、船の行をロックしてから調べます。
  • 作業船の登録は管理者だけです。いまの7隻はデモ（架空の船・架空の動き）で、AIS は未接続です。

18.6測量の比較（サーバ版・海上工事）

  • 深浅測量を測量日ごとに登録します（XYZ／CSV。標高 T.P.・標高 DL・水深 DL の3形式）。DL の T.P. からの高さは潮位表の公表値が初期値で、無い地点は入力が必要です。ブラウザで現場の格子に直してから送ります。
  • 測量日ごとの残り土量・出来高（測量）・余掘り（過盛り）の推移を出します。土量はワールドモデルと同じ計画面・同じメッシュ法で計算します（台帳の測量で WM の土量と一致することを検査で確認）。
  • 選んだ測量の出来形の色分け：浚渫は計画より 0.1m 以上浅いと取り残し、0.5m を超えて深いと余掘り超過。埋立は ±0.3m（サンプル値。marine.surveyTolerance）。
  • 2つの測量の変化（深くなった・浅くなった m³）を出します。「B の海底で土量・工程を計算し直す」はその画面だけで、保存せず、他の人の画面も変わりません。

18.7協議・区域（サーバ版）

18.8遅れの分析

竣工予測と、遅れの理由（実績の遅れ・実効率・ボトルネック・冬期・雨天・搬入土）を計算から文章にし、遅れを取り戻す編成（台数・稼働時間・稼働日）を予測し直して3案まで提案します。「試す」で What-if に入れます。サーバ版では「遅れの推移」（毎朝の記録。19.4）も出します。AI による文章化（任意・既定は無効）を有効にすると、計算の結果だけを claude-opus-5-5 に送り、400字以内の説明文にします（数値はワールドモデルの計算が正）。

18.9類似工事

総合評価部向けに、同じ工種で土量が 0.5〜2 倍の工事（無ければ同じ工種、それも無ければ同じ工種区分）の工期・土量・能力・遅延・実効率を表と散布図で比べます。全国表示のポートフォリオには工種別の平均を出します。現場は架空の17件なので、統計としての意味はまだありません。

18.10実績入力

工程ごとの出来高を入れると、実効率 η を較正し直して竣工予測・遅延・3D が変わります。サーバ版では編集者・管理者が入力するとデータベースに保存され、ログインした全員に反映されます（変更の履歴が残る）。閲覧者は入力できません。静的な配信・埋め込み版では、このブラウザにだけ保存するデモです（JSON で書き出し・読み込み）。サンプルの実績は架空です。

19遅れの予兆（日次の記録・判定・通知）

19.1ねらい

遅れが急にふえた現場を、支店会議を待たずに見つけるため、毎朝の正式な予測を記録して前の記録と比べます。サンプルの実績は固定なので、実績の入力が無い間は遅れの変化はほぼ 0 です。

19.2日次の記録（毎朝 7:30 の定時処理）

  1. systemd の mirai-3d-portal-daily.timer が毎朝 7:30（最大 2 分の揺らぎ。電源が切れていた日は起動後に1回）に tools/daily_job.py を動かします。
  2. サーバの上でデータベースの台帳・実績を読み、このサーバの画面をヘッドレスのブラウザで開いて、同じ計算（ワールドモデル）に渡します。画面の /api への問い合わせはこの処理の中で答えるので、ログインはしません。新しいアカウント・パスワード・書き込み用の API は作りません。Google 実写3D は使いません（地形は国土地理院から取得）。
  3. 全現場の正式な予測（初期計画の編成＋実績で較正した実効率。What-if は含まない）から、遅れの日数・予測竣工日・実績と計画の進捗・実効率を求め、データベースへ直接 1現場1日1行で保存します（同じ日に再実行したら上書き）。
  4. 国土地理院から地形を取得できなかった現場があっても、取得できた現場は記録します（その日に再実行すれば埋まる）。
  5. 続けてメールの判定（19.5）をします。CI では動かしません。

過去の記録はさかのぼって作りません。判定は記録が7日分たまってから（比べる記録が無い現場は判定しない）です。

  • 土量（切土・盛土・残土・搬入土）：計算結果の m³ を、小数点以下を四捨五入して整数にしています（0.5 はつねに切り上げ）。そのため、表の値どうしを計算しても1m³ ずれることがあります。

  • 実績／計画：アプリが％の整数に四捨五入した値（JavaScript の Math.round）そのままです。
  • η：小数第3位を四捨五入しています。
